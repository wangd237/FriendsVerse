# FriendsVerse — Story Prototype 详细产品规格

**版本**：v0.4.0（技术方案衔接）  
**日期**：2026-10-23  
**状态**：待开发；不代表已完成模拟或验收  
**上位需求**：[PRD.md](PRD.md) · 角色设计：[CHARACTER_DESIGN.md](CHARACTER_DESIGN.md) · 世界与交互：[WORLD_INTERACTION.md](WORLD_INTERACTION.md) · 技术设计：[STORY_PROTOTYPE_TECHNICAL_DESIGN.md](STORY_PROTOTYPE_TECHNICAL_DESIGN.md) · 决策来源：[DECISIONS.md](DECISIONS.md)

> 本文是第一阶段 Story Prototype 的实施前产品规格，用于回答「什么内容应由 Agent 自主产生、观众最后看到什么、怎样评估体验」。具体模型、数据库、调度框架仍不在本阶段锁定。

## 1. 阶段目标与范围

工程实施细节请参考 **[Story Prototype Technical Design](STORY_PROTOTYPE_TECHNICAL_DESIGN.md)**，该文给出候选 Python/SQLite 实现、角色动作契约、模拟/剪辑/提交的一致性边界与 T0–T3 递进验收。此文件仍作为七集内容和体验验收的主规格，不应被技术选型取代。


**核心验证问题**：6 位角色在有初始人格、个人记忆、独立认知与共同环境的条件下，是否能生成值得连续观看的轻喜剧情景剧，并出现**有证据的跨集关系演化**？

### 1.1 预期交付物
- 一个可手动执行「初始化宇宙 → 生成下一集」的**最小可运行原型**，可以先用命令行而不是完整 Web。
- 同一世界连续生成 **7 集**情景剧剧本，约对应七个虚拟日；建议每集 3–5 场、3–6 分钟阅读量，允许较短而不强制凑数。
- 每集具有可定位的原始模拟事件、人物关系变化证据、前后世界状态与生成运行记录。
- 一份人工试读和故事质量报告。

### 1.2 阶段内不做
Web 剧集大厅和关系图可暂用文档/简单查看器替代；不做视频、配音、角色动画、用户进入世界、多人在线、剧情树和复杂经济系统。

### 1.3 内容边界
基于《老友记》六位经典主角的私人粉丝实验概念；原创日常事件和对白，不复制原剧剧本或演员形象。公开发行需授权或改为原创 IP。

## 2. 最小用户体验

1. 用户「开启一个新宇宙」：使用**固定且可复现**的角色背景、初始关系、世界地点；得到 Universe ID。
2. 用户点击「生成 EP01」：系统推进一个虚拟日，自动完成角色行动、对话、状态更新和剧集编排。
3. 用户阅读 EP01：按场景显示地点/时间、必要动作和对白；结束后看到「发生了什么 / 哪些关系改变」。
4. 用户点击「下一集」：必须沿用已提交的世界与角色记忆；不从零开始。
5. 用户随时查看此前剧本及变更来源，不重新生成已发布内容。
6. 生成失败：不发布半成品，不覆盖前一集；可重试同一集。

### 2.1 推荐剧集结构
- 标题：根据已发生的事件拟定，例如《The One With the Missing Sandwich》，不可先确定剧情再强迫世界实现。
- 简短前情：仅包含观众已知、与本集相关的事实。
- 正文：通常 3–5 场（SCENE，地点 + 时间 + 台词 + 精简动作）。
- 片尾：本集关键事件、关系变化及证据引用；无重要变化时如实显示「暂无重大关系变化」。
- **不强制每集六人出场，不强制每集有冲突、和解或悬念。**

## 3. 第一季世界基线（设计提案，非最终锁定）

### 3.1 初始角色

下表仅供概览。人格核心、冲突倾向、修复方式、主观记忆边界和完整初始关系以 **[Character Design](CHARACTER_DESIGN.md)** 作为 Story Prototype 的角色细化提案。该细化不要求预设台词、恋爱结局或关系精确数值。


| 角色 | 稳定 Persona 核心 | 独立长期目标 | 喜剧化但不刻板的弱点 |
|---|---|---|---|
| Monica | 细心、好胜、重视朋友、喜欢秩序 | 提升厨艺与职业成就 | 遇到计划失控时容易较真 |
| Rachel | 感性、时尚、愿意成长 | 增强职业独立性 | 决策时可能摇摆 |
| Phoebe | 独立、善良、想法独特 | 音乐创作与自主生活 | 偶尔用离奇逻辑解释事情 |
| Ross | 博学、认真、敏感 | 兼顾学术和私人生活 | 容易过度解释或钻牛角尖 |
| Chandler | 幽默、忠诚、习惯用讽刺缓解尴尬 | 维系友情、探索工作外的满足感 | 不善于直面严肃情绪 |
| Joey | 乐观、热情、重情义、热爱食物 | 争取演员机会 | 有时冲动，理解发生偏差 |

**注意：** 「稳定 Persona」不等于角色永远重复同一种反应。允许成长；不强制复现原剧中既定恋爱或职业轨迹。

### 3.2 初始社会关系
- Ross 与 Monica 为兄妹。
- Chandler 与 Joey 是室友兼好友。
- Monica 与 Rachel 是室友兼好友。
- 其余四人之间已有基本熟识与友情；具体亲密度、信任度、矛盾度**初始数值暂不锁定**。
- 不预置「指定人物必须成为情侣」或「第 N 集吵架」这类结果性目标。

### 3.3 地点与时间

世界地图、时段、主动社交、先产生意向再解析会面的规则及无事件日验证见 **[World & Interaction Design](WORLD_INTERACTION.md)**。这里保留原型高层约束，避免重复指定另一套会面逻辑。

最小地图：Monica/Rachel 公寓、Chandler/Joey 公寓、公共走廊、Central Perk；Ross/Phoebe 的家及工作场所可作为**抽象地点**，无须渲染完整地图。

时间：每次生成一集代表一个虚拟日；内部可划分早晨/下午/晚上，平淡日程用规则推进，不对每个小时的每位角色强制发起 LLM 调用。角色需在可见或可通信时才发生有效互动。

## 4. 角色自主行为的产品规则

### 4.1 一次决定的必要输入
- 稳定 Persona 与个人目标。
- 当前处境（地点、时间、环境事件、在场人物、可用动作）。
- 私有记忆与当前未解决的承诺/矛盾。
- 对现场其他人的主观关系及**自己知道的事实**。

### 4.2 最小行动集合
`move_to`（移动）、`speak`（说话）、`do`（当前地点可执行的简单行动）、`wait`（等待）。必要时可以通过事件或对话承诺表达目标，不在原型期扩展几十种工具。

### 4.3 世界引擎负责的硬约束
- 空间：不在场就不能当面听见对话；不能越过场景限制任意移动。
- 认知：角色私密信息不自动共享；被告知的信息也可保留不同主观解读。
- 时间：事件必须按发生顺序处理；不能在已过去的场景中行动。
- 事实：状态变化（位置、物品、承诺）经执行或记录后才生效；模型不能通过一句旁白直接改写整个世界。
- 交互：同场多人交流时使用有限对话轮次和终止条件，避免无限寒暄。
- 成本：普通作息优先用规则跳过；达到预算时保留已完成状态并受控结束，不胡乱编造余下行动。

## 5. 人物关系与记忆

### 5.1 关系模型
方向性：`A → B` 和 `B → A` 独立，可不同。

拟采用三个可解释维度（**取值范围及变化规则待实验校准**）：
- `closeness`：亲密程度与主动相处倾向。
- `trust`：认为对方可靠、真诚的程度。
- `tension`：存在未解决摩擦的程度。

关系并非每次对话都更新，也不要求为每集制造关系波动。

### 5.2 关系事件
一个有效的关系变化至少含：关系方向、发生时间、触发事件 ID、具体行为证据、变化原因和变化后的状态。事件例子：主动帮助、兑现或违背承诺、解释误会、公开支持、发生争执；轻微玩笑不能自动等于信任下降。

### 5.3 记忆分层（产品要求，非指定技术）
- **世界事实**：客观已经发生什么，供一致性验证。
- **个人经历**：某个角色实际看到、听到、说过、做过什么。
- **个人信念**：角色如何理解这件事，可能与真相不同。
- **未完事项**：待履行的约定、误会、目标与持续影响。

例子：Chandler 忘记答应过的排练；Joey 记得失约并感到失望。系统不能把 Joey 的心情瞬间注入 Chandler 的私有认知，除非他有机会得知。

重要未结事项不可因普通记忆压缩而消失；角色发生观点改变应有新的经历依据。

## 6. 如何自然产生有趣故事

### 6.1 「故事机会」不是「预设剧本」
每个可投放事件只定义：
- 触发条件与发生地点；
- 新的客观事实或可观察刺激；
- 哪些角色可以知道它；
- 可以继续发展的可能性（**仅供编辑/评估，不下发人物反应指令**）。

例：Joey 收到试镜邀请是事件机会；「Chandler 羡慕、Joey 生气、两人和解」是禁止预设的剧情结局。

### 6.2 原型事件池（候选）
| 生活机会 | 允许的客观刺激 | 不强制的互动方向 |
|---|---|---|
| 工作机会 | Joey 收到试镜通知 | 朋友能否帮助、是否出现误解 |
| 聚会机会 | Monica 打算邀请朋友来家中吃饭 | 准备过程中出现不同期待 |
| 物品问题 | 一份快递送错公寓 | 多人猜测、协调归还 |
| 咖啡馆变化 | Central Perk 某个设施暂不可用 | 对习惯造成扰动 |
| 职业犹豫 | Rachel 得到一则工作招聘信息 | 讨论、支持或意见不同 |

建议每个虚拟日**最多提供一个主动新增的主要生活刺激**；可有无事件日。角色仍可自发开始交流和其他行动。

### 6.3 保证「好看」而不牺牲「自主」
- 可以在**模拟开始前**安排可观察的日常机会，不能在模拟完成后虚构人物行为。
- 如果某天互动较少：可以较短篇幅交付，或在**模拟尚未结束时**添加符合世界规则的轻量环境机会；需记录注入事件并可复盘。
- 笑点应来自真实角色对白、反差、误会或前情呼应（callback）；剪辑不能把未说过的玩笑塞给角色。
- 多场戏应围绕一个或两个自然浮现的故事焦点；不要把所有无关聊天拼成流水账。

## 7. 模拟到剧本的内容生产契约

1. **Generate**：引擎推动虚拟日，角色依次/按场景互动。
2. **Record**：日志记录每次真实行动和对白，生成稳定 `event_id`；记录角色可见范围。
3. **Update**：根据事件更新世界事实、个人记忆与关系；变化要绑定证据。
4. **Select**：筛选重要、有趣、能推动后续关系的场景，省略平淡日程。
5. **Edit**：只补充场景标题、时间、简单旁白与节奏性分段；不更改核心行动、说话者、原始对白含义、事件先后与既有世界事实。**第一版优先原样保留关键对白。**
6. **Verify**：对每场对话/关键动作检查对应原始 `event_id`；验证角色知识、时间、地点、状态更新和关系变化的一致性。
7. **Publish**：同一集的剧本、事件日志和最终世界状态作为同一批次提交；失败不能半提交。

**建议输出结构**（是信息契约，不锁定存储形式）：
- `episode_id`, `universe_id`, `virtual_day`, `title`, `recap`, `scenes[]`
- `scenes[]` 中每个段落可追溯到 `source_event_ids[]`
- `events[]`: 行动者、参与者、时间/地点、行动或对白、可见者、事件 ID
- `relationship_changes[]`: 有向关系、变化、`source_event_ids[]`
- `world_state_before / world_state_after`
- `generation_trace`: 角色调用、失败/重试、LLM 调用次数/估算成本（有真实用量时优先真实用量）

## 8. 七集实验方案：只固定刺激，不固定剧情

**推荐实验日程（可调整）**：
| 虚拟日 | 环境策略 | 产品观察点 |
|---|---|---|
| Day 1 | 不投放重大事件，允许自然相遇 | 人物辨识度、基础生活合理性 |
| Day 2 | 一个轻量生活扰动（如错送快递） | 能否产生自然幽默/误会 |
| Day 3 | 与一名角色目标有关的机会（如试镜） | 朋友是否会自发回应 |
| Day 4 | 无强制事件 | 前几天的事情是否持续影响行为 |
| Day 5 | 一个群体聚集机会（如聚餐） | 多人场景对白和人物反差 |
| Day 6 | 无强制事件 | 是否有未完关系线自发回返 |
| Day 7 | 普通日常，可使用环境小扰动 | 能否自然收束一些关系并保留开放性 |

**严格禁止**：提前写好七集标题、台词、人物冲突、恋爱结局、和好时间。上述是可复现实验刺激，不是正式季播日程。若 Day 4 没有产生「续篇」，也要如实记录而非补写。

## 9. 质量验收与 Go / No-Go

### 9.1 事实与运行门槛（硬门槛）
- 同一 Universe 连续产出 7 集；生成失败可恢复且不重复发布。
- 关键动作/对白都有可定位的源事件；重要关系变化都有证据。
- 无严重时空错误、明知不该得知的全知视角、角色基本身份混乱。
- 曾发生的关键承诺和未解决矛盾，后续合理情境中不应无故遗忘。
- 各集生成耗时、调用量、失败/重试原因可观测；预算阈值通过实验设置。

### 9.2 内容体验（人工验证）
邀请 3–5 位目标用户试读，逐集以 1–5 分评价：
1. 角色辨识度（仅看对白/行为能否区分人物）；
2. 幽默与温暖程度；
3. 事件因果和跨集连续性；
4. 关系演化可信度；
5. **是否愿意马上看下一集**（主指标），记录不愿继续的具体原因。

体验门槛先做**探索性 Go/No-Go 评审**：若出现系统性人格崩坏、流水账或多数试读者缺乏追剧兴趣，应先改进内容机制，不进入完整 Web 开发。小样本结果不用于证明实际留存率。

### 9.3 对照实验（推荐，非 P0）
同一初始种子比较「无长期记忆」与「保留长期记忆」，检查连贯性和关系可信度，避免只展示一次随机的成功案例。资源允许时可补充固定脚本对照以了解自主性与故事质量的取舍。

## 10. 设计边界与待确认问题

- **当前设计建议**：一虚拟日一集、六位角色、有限场景、3 个有向关系维度、以 CLI/文档为首个原型出口。
- **待评审**：初始关系的数值、具体事件触发策略、行动 API、模型选择、记忆压缩实现、单集预算、内容质量判定阈值。
- **不要混淆**：通过七集实验≠已经验证普通用户的长周期留存，故事「由 Agent 产生」也≠不存在系统提供的环境刺激。
